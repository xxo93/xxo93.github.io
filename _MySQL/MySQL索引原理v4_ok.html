B+ 树结构
B+ 树是 InnoDB 的默认索引结构。所有数据存储在叶子节点，叶子节点通过链表相连，支持高效范围查询。左键拖动单个节点可调整布局，右键拖动画布，滚轮缩放。
🌳

多路平衡

每个节点可有多个子节点，树高通常 3~4 层即可存储千万级记录。

📄

数据在叶子节点

内部节点只存索引键和指针，所有实际数据都在叶子节点中。

🔗

叶子节点链表

叶子节点通过双向指针相连，支持高效的范围查询（BETWEEN、ORDER BY）。

⚡

查找效率 O(log n)

树高即磁盘 I/O 次数，1500 万条记录通常只需 3~4 次 I/O 即可定位。

⚠️ 本页尺度说明（教学简化）
为了让 15 行数据的树形结构肉眼可见，本页把每节点扇出与叶子容量都设为 4，因此只有 2~3 层。 真实 InnoDB 中，一个节点就是一个 16KB 的数据页：
内部页可容纳 ≈ 1200 个 (键, 页号) 对 -- 假设主键 BIGINT(8B) + 页号(6B) = 14B，16384 / 14 ≈ 1170 叶子页可容纳 ≈ 100 ~ 200 行完整记录 -- 取决于行宽 树高 2 层 ≈ 1200 行 树高 3 层 ≈ 1200 × 1200 ≈ 144 万行 树高 4 层 ≈ 1200 × 1200 × 100 ≈ 14 亿行
所以「千万级数据只需 3~4 次磁盘 I/O」说的是真实扇出（约 1200）下的树高， 不是本页画面上的层数。本页的一次「节点跳转」对应真实环境中的一次「页读取」。
B+ 树 vs B 树
B+ 树（MySQL 使用）
数据只在叶子节点 → 内部节点更小 → 每页存更多索引键 → 树更矮 → I/O 更少。叶子链表支持范围扫描，且所有查询路径长度一致（都走到叶子），性能稳定。
B 树
数据在所有节点 → 内部节点更大 → 树更高 → 更多 I/O。命中内部节点时可提前返回，但无叶子链表，范围查询需要中序回溯。
聚簇索引（Clustered Index）
聚簇索引将数据行直接存储在 B+ 树的叶子节点中——「索引即数据」。找到主键就直接拿到了完整行，无需额外查找。InnoDB 表必有且仅有一个聚簇索引：有主键用主键，无主键用第一个非空唯一索引，都没有则生成隐藏的 6 字节 DB_ROW_ID。

为什么二级索引不直接存整行数据？
① 省空间：一张表可能有 5~6 个二级索引，若每个都存整行，存储成本翻数倍，缓冲池命中率也会暴跌。
② 降低维护成本：数据行只存在聚簇索引一处，UPDATE 非索引列时不必同步修改所有二级索引。
③ 主键变更代价可控：存主键值而非物理地址，页分裂/合并导致行移动时，二级索引无需更新（代价是主键不宜过大，见「索引优化 → 页分裂与自增主键」）。
覆盖索引（Covering Index）
当查询所需的所有字段都包含在索引中时，MySQL 无需回表，直接从索引返回结果。切换下方查询模式，观察回表虚线的出现与消失——这是两种模式最直观的差别。

最左前缀原则速查
索引 (a, b, c)
✓ WHERE a=1 · ✓ WHERE a=1 AND b=2 · ✓ WHERE a=1 AND b=2 AND c=3
✓ WHERE a>1（范围列本身可用，但其后的 b、c 用不上）
⚠ WHERE a=1 AND c=3（只用到 a，c 需回表后逐行过滤）
✗ WHERE b=2 · ✗ WHERE c=3 · ✗ WHERE b=2 AND c=3
MySQL 8.0 例外：Index Skip Scan。 当首列基数（distinct 值个数）很低时，优化器可能对首列的每个取值分别做一次子查询， 从而「跳过」最左列。例如索引 (gender, age) 上执行 WHERE age = 25，EXPLAIN 的 type 会显示 range 而非全表扫描。
但这依赖统计信息且首列基数必须足够小，不能当作可以省略最左列的理由——设计索引时仍应遵守最左前缀。 另：ORDER BY 中的 ASC/DESC 混用会破坏索引有序性（8.0 可用降序索引解决）。

找涉及列

STEP 2
评估选择性
SELECT COUNT(DISTINCT col)/COUNT(*)，接近 1 才值得建；性别/标志位放弃
STEP 3

联合索引：等值列在前，范围列在后；同列排按选择性高的在前
STEP 4

STEP 5

🔍 EXPLAIN 执行计划 · 关键字段速查
EXPLAIN 加在 SELECT 前，输出一行/多行计划。下面两个字段最值得盯：
type 字段（访问类型，从好到差） 含义
system / const表只有一行 / 主键或唯一索引等值匹配，最快
eq_refJOIN 时用主键/唯一索引，每行匹配一行
ref非唯一索引等值匹配，命中多行
range索引范围扫描（BETWEEN / > / LIKE 'x%'）
index全索引扫描（扫描整棵索引树），仍需警惕
ALL⚠️ 全表扫描，必须优化
Extra 字段 含义与判读
Using index✅ 覆盖索引，无需回表
Using index condition✅ 索引下推 ICP 生效
Using whereServer 层过滤，正常但不一定最优
Using filesort⚠️ 需要额外排序，考虑让 ORDER BY 走索引
Using temporary⚠️ 用临时表（常见于 GROUP BY），需优化
其他字段：key 实际用的索引（NULL = 没用上）、key_len 用了几列联合索引（见 D5）、rows 预估扫描行数、filtered 过滤后剩余百分比。一条慢 SQL 的诊断顺序：type → key → key_len → rows → Extra。
🧪 实战案例：一条慢 SQL 的三次优化

背景： users 表 100 万行，有 id 主键、name、age、dept 列。业务上高频执行这条查询：

SELECT id, name, age FROM users WHERE dept = '技术部' AND age > 25 ORDER BY age LIMIT 10;

① 初始状态：无合适索引

-- EXPLAIN 输出（节选） type: ALL key: NULL rows: 987,654 Extra: Using where; Using filesort -- 全表扫描 + 文件外排序，响应 ~1.2s

② 第一次优化：建联合索引 (dept, age)

ALTER TABLE users ADD INDEX idx_dept_age (dept, age); -- 复查 EXPLAIN type: range key: idx_dept_age key_len: 86 -- dept VARCHAR(20)=82B + age INT=4B，两列都用到了 ✅ rows: 12,340 Extra: Using where; Using filesort -- 扫描行数降到 1.2 万，响应 ~45ms。但 ORDER BY age 仍 filesort？
为什么 range 后还 filesort？因为 dept='技术部' 是等值、age>25 是范围，B+ 树在 (dept, age) 上同一 dept 内 age 是有序的， 理论上应该能避免 filesort——但优化器选了 range 而不是 ref，且 LIMIT 10 下优化器觉得走索引回表 12 万行不如全表 + filesort 快。

③ 第二次优化：把 name 纳入索引，走覆盖索引

ALTER TABLE users DROP INDEX idx_dept_age; ALTER TABLE users ADD INDEX idx_dept_age_name (dept, age, name); -- 复查 EXPLAIN type: range key: idx_dept_age_name rows: 12,340 Extra: Using index condition; Using index -- Extra 出现 Using index = 覆盖索引，不回表； -- 索引叶子节点里 (dept, age, name, id) 已包含 SELECT 全部列，响应 ~3ms

阶段 type 扫描行数 Extra 耗时
