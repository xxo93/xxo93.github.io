模块一 · 打底

事务基础与隔离级别

在理解 MVCC 和锁之前，先搞清楚一件事：数据库为什么需要「事务」？多个操作同时读写同一批数据时，会出什么乱子？

一、事务到底是什么

事务（Transaction）就是一组必须「要么全做完、要么全不做」的数据库操作。它不是一条 SQL，而是一个有始有终的工作单元。

生活化类比：银行转账

你要给朋友转 100 元。这背后其实是两个动作：① 你的账户减 100；② 朋友的账户加 100。如果做完第①步就断电了，钱凭空消失了 100 元——这是灾难。银行系统必须保证这两步捆在一起：要么都成功，要么都不发生。这个「捆绑起来的工作单元」就叫事务。

SQL 示例 · 一个最典型的事务 
-- 开启事务
BEGIN;   -- 或 START TRANSACTION

-- 步骤1：A 扣款
UPDATE account SET balance = balance - 100 WHERE id = 1;

-- 步骤2：B 收款
UPDATE account SET balance = balance + 100 WHERE id = 2;

-- 全部成功 → 提交，永久生效
COMMIT;

-- 中途出错 → 回滚，像什么都没发生过
-- ROLLBACK;

在 BEGIN 和 COMMIT 之间的所有操作，对外界来说是一个不可分割的整体。执行到一半时，别的连接看不到这些还没提交的改动。

二、ACID：事务的四条承诺

数据库对事务做了四个保证，简称 ACID。这四条也正是 MVCC 和锁存在的原因。

A · 原子性 Atomicity

一组操作要么全成功，要么全撤销。
靠什么实现：undo log（回滚日志）

C · 一致性 Consistency

事务前后数据都符合业务规则（比如总额不变）。
靠什么实现：是最终目的，由 A、I、D 共同保证

I · 隔离性 Isolation

多个事务并发时，彼此不互相干扰。
靠什么实现：MVCC + 锁 ← 本篇主角

D · 持久性 Durability

提交后的数据即使断电也不会丢。
靠什么实现：redo log（重做日志）

划重点

隔离性是四条里最难做的。原子性和持久性只关心「一个事务自己」，靠日志就够了；而隔离性要处理「多个事务同时动手」的冲突，这才需要 MVCC 和锁这两套机制出场。

三、并发会出什么乱子：三种「读异常」

如果完全不做隔离，让事务们随意读写同一批数据，会出现三类经典问题。搞清楚这三种问题，才能理解隔离级别到底在防什么。

事务 B 修改了一行但还没提交，事务 A 就把这个中间值读了出来。随后 B 回滚了，A 手里的数据从来没真实存在过。

时刻事务 A事务 B问题
T1UPDATE user SET salary=9000 WHERE id=1
未提交		原值 5000 被改成 9000
T2SELECT salary FROM user WHERE id=1
→ 读到 9000		脏读发生
T3ROLLBACK → 工资恢复 5000A 拿到的 9000 是幻影
类比

你在群里看到同事发了「我辞职了」，转头他跟你说「刚才打错字撤回了」。你已经按「他要走」安排了工作——这就是基于脏数据做的决策。

事务 A 在同一个事务内两次读同一行，中间事务 B 提交了一次 UPDATE，导致 A 两次读到的值不同。注意：这里 B 是已提交的，所以数据是真实的，问题在于 A 自己「不自洽」。

时刻事务 A事务 B说明
T1BEGIN
T2SELECT salary... → 5000第一次读
T3UPDATE ... SET salary=9000
COMMIT		B 合法提交
T4SELECT salary... → 9000同一事务内值变了

与脏读的区别：脏读读到的是「未提交的假数据」；不可重复读读到的是「已提交的真数据」，只是前后不一致。

事务 A 按范围查询（比如 WHERE salary > 3000），事务 B 在这个范围里 INSERT 了新行并提交。A 再查一次，凭空多出来几行——像幻觉一样，所以叫幻读。

时刻事务 A事务 B说明
T1SELECT COUNT(*) FROM user WHERE salary>3000
→ 3 行		第一次统计
T2INSERT INTO user VALUES(9,'小王',8000)
COMMIT		插入了符合条件的新行
T3SELECT COUNT(*) ...
→ 4 行		多出一行「幻影」
关键区分

不可重复读针对「已存在的行被改值」，幻读针对「范围里多出/少了行」。前者用行锁就能挡住，后者必须锁住「行与行之间的空隙」——这正是间隙锁（Gap Lock）登场的理由，我们在模块三会详细讲。

四、四种隔离级别：用「允许出什么问题」来定义

SQL 标准定义了四个隔离级别。它们的本质区别不是「加了什么锁」，而是「允许上面三种读异常里的哪几种发生」。级别越高越安全，但并发性能越差。

InnoDB 的默认与特别之处

MySQL InnoDB 的默认隔离级别是 可重复读（REPEATABLE READ，简称 RR）。而且 InnoDB 在 RR 级别下通过「MVCC + 间隙锁」的组合，在大多数场景下连幻读也一并解决了——这比 SQL 标准对 RR 的要求更严格。这套配合机制正是模块四的核心内容。

SQL · 查看和修改隔离级别 
-- MySQL 8.0：查看当前会话的隔离级别
SELECT @@transaction_isolation;

-- 设置当前会话为可重复读
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- MySQL 5.7 用的是 tx_isolation（8.0 已废弃）
SELECT @@tx_isolation;

五、铺垫：为什么需要 MVCC 和锁

看完上面四种级别，一个自然的问题是：数据库到底怎么做到「挡住」这些异常的？思路只有两条：

🔒
思路一：加锁排队
写的时候锁住数据，别人只能等。简单直接，但读写互相阻塞，并发性能差。
＋
📸
思路二：多版本快照
给数据存多个历史版本，读的时候拿一份「老照片」看，不用等写事务。这就是 MVCC。

InnoDB 的高明之处在于两者都用，而且分工明确：普通的 SELECT 走 MVCC 快照，完全不加锁；只有 UPDATE / DELETE / SELECT ... FOR UPDATE 这类会改变或必须读到最新值的操作才加锁。这样「读不阻塞写、写不阻塞读」，并发性能大幅提升。

接下来的两个模块，我们分别拆开看这两套机制的内部构造。

模块一小结

  1. 事务 = 一组不可分割的操作，通过 BEGIN / COMMIT / ROLLBACK 控制边界。
  2. ACID 四条承诺中，隔离性最难，因为它要处理多事务并发冲突；原子性靠 undo log，持久性靠 redo log，隔离性靠 MVCC + 锁。
  3. 三种读异常层层递进：脏读（读到未提交的假数据）→ 不可重复读（同一行前后值变了）→ 幻读（同一范围行数变了）。
  4. 四种隔离级别 = 允许哪几种异常发生。级别越高越安全，并发越差。
  5. InnoDB 默认 RR，且额外用间隙锁在多数场景下也解决了幻读。
  6. MVCC 与锁的分工：快照读不加锁，当前读才加锁 —— 这是理解后续一切内容的钥匙。
模块二 · 核心机制

MVCC 原理：不加锁也能读到一致数据

MVCC = Multi-Version Concurrency Control，多版本并发控制。它的核心思想一句话：不去改原来那行数据，而是每次修改都留下旧版本，读的人自己挑一个合适的版本来看。

一、先建立一个直觉：老照片

生活化类比：装修前的老照片

你把客厅重新装修了，但你手里还留着装修前拍的照片。朋友问「你家客厅原来什么样」，你不用把装修拆掉，直接翻照片就行。

MVCC 就是这个思路：数据库改数据时，不会销毁旧值，而是把旧值存进「相册」（undo log）。别的事务想看旧样子，翻相册即可，完全不用等你装修完（不用等写事务提交）。这就是「读不阻塞写、写不阻塞读」的由来。

那么问题来了：数据库怎么知道「相册里的哪一张」才是某个事务该看的版本？答案分三步——隐藏列（给每个版本贴标签）、版本链（把版本串起来）、ReadView（判断哪个版本对我可见）。

二、第一步：隐藏列 —— 每行数据的「身份证」

你建表时只写了 id、name、salary 三个字段，但 InnoDB 在磁盘上实际存储时，会偷偷给每一行加上几个你看不见的列。这就是隐藏列。

InnoDB 每行数据的隐藏列（也叫「行记录隐藏字段」）
隐藏列名占用作用通俗理解
DB_TRX_ID6 字节 记录最后一次修改这行的事务 ID。每次 UPDATE / DELETE 都会更新它。 「这张照片是谁拍的」
DB_ROLL_PTR7 字节 回滚指针，指向 undo log 中这行的上一个版本。版本链就是靠它串起来的。 「翻到相册的上一页」
DB_ROW_ID6 字节 隐式主键。仅当表没有主键、也没有非空唯一索引时才由 InnoDB 自动生成。 「没有身份证就给个临时编号」
DB_DELETE_FLAG
聚簇索引记录头		1 bit 删除标记。DELETE 并不立刻物理删除，只是把这个标记位设为 true，真正的清理由后台 purge 线程完成。 「贴张作废标签，先不撕掉」
为什么 DB_TRX_ID 是 MVCC 的地基

有了 DB_TRX_ID，每个数据版本就带上了「出生时间戳」。事务之间可以比大小：ID 小的说明开启得早。后面 ReadView 判定可见性，本质上就是在比事务 ID 的大小。

SQL · 建表语句 vs 实际存储 
-- 你写的建表语句
CREATE TABLE employee (
  id     INT PRIMARY KEY,
  name   VARCHAR(20),
  salary INT
);

-- InnoDB 实际存储的「逻辑结构」（隐藏列无法用 SQL 查到）
-- ┌────────┬────────┬──────────┬─────────────┬───────────────┐
-- │   id   │  name  │  salary  │ DB_TRX_ID   │ DB_ROLL_PTR   │
-- ├────────┼────────┼──────────┼─────────────┼───────────────┤
-- │   1    │  张三  │   5000   │    90       │  → undo log   │

-- 想间接看到版本信息，可以查这个内部视图（8.0）
SELECT * FROM information_schema.innodb_trx;   -- 当前活跃事务及其 trx_id

三、第二步：undo log 与版本链

每次修改一行数据，InnoDB 会先把修改前的旧值写进 undo log（回滚日志）。然后通过 DB_ROLL_PTR 把「新值 → 旧值 → 更旧的值」串成一条链，这就是版本链。

类比：串起来的相册页

相册第 1 页是最早的样子，每拍一张新照片就插在最前面，并在新照片背面写「上一页在相册第 N 页」。你想找某个时间点的样子，就从最新的一张往回翻，一直翻到符合你要求的那张为止。

undo log 的两个身份

身份一（回滚用）：事务执行 ROLLBACK 时，靠 undo log 把数据还原——这实现了 ACID 的原子性。
身份二（MVCC 用）：别的事务通过版本链读取历史版本——这实现了 ACID 的隔离性。
同一份日志，干了两件事。

注意 · 长事务为什么是性能杀手

只要还有一个老事务没提交，它可能需要读的所有旧版本就都不能被 purge 清理。长事务会导致 undo log 无限膨胀、版本链越来越长，每次读都要顺着链翻很多层，性能急剧下降。生产环境中「未提交的长事务」是常见的故障源，可以用 SELECT * FROM information_schema.innodb_trx ORDER BY trx_started 排查。

四、第三步：ReadView —— 决定「哪个版本对我可见」

版本链上有一堆版本，读的时候到底该拿哪一个？InnoDB 的答案是：事务在做快照读时，先给自己生成一个ReadView（一致性视图），用它来判断链上每个版本的可见性。

ReadView 里的四个字段

字段含义怎么得到
m_ids生成 ReadView 时，当前还「活跃」（未提交）的事务 ID 列表扫一遍事务链表，把没提交的都记下来
min_trx_idm_ids 里的最小值最小的活跃事务 ID
max_trx_id系统即将分配给下一个事务的 ID（不是 m_ids 最大值！）当前全局最大事务 ID + 1
creator_trx_id创建这个 ReadView 的事务自己的 ID自己是谁

可见性判定算法（核心中的核心）

拿到版本链上某个版本的 DB_TRX_ID（下面记作 trx_id），按顺序问四个问题：

① 可见
trx_id == creator_trx_id
这个版本是我自己改的 → 当然可见。
↓
② 可见
trx_id < min_trx_id
这个版本在我创建视图之前就已经提交了 → 可见。
↓
③ 不可见
trx_id ≥ max_trx_id
这个版本是在我创建视图之后才开启的事务改的 → 太新了，不可见。
↓
④ 看情况
min_trx_id ≤ trx_id < max_trx_id
落在中间地带，就看 trx_id 在不在 m_ids 里：
在 m_ids 里 → 说明生成视图时它还没提交 → 不可见；
不在 m_ids 里 → 说明它已经提交了 → 可见。

如果某个版本判定为「不可见」，就顺着 DB_ROLL_PTR 取上一个版本，重新走一遍这四步，直到找到一个可见的版本为止。找到的那个，就是这次 SELECT 的结果。

ReadView 什么时候生成？—— RR 与 RC 的分水岭

这是最容易被问到的面试题，也是 RR 和 RC 唯一的行为差异来源：

隔离级别ReadView 生成时机直接后果
RR 可重复读 事务内第一次快照读时生成，之后整个事务复用同一个 不管别人提交了多少次，我读到的永远是那一刻的世界 → 可重复读
RC 读已提交 每次快照读都重新生成一个新的 ReadView 每次读都能看到别人最新提交的值 → 必然出现不可重复读
一句话记住

RR 和 RC 用的是同一套 MVCC 机制、同一套判定算法，唯一的区别就是 ReadView 是「生成一次用到底」还是「每次读都重新生成」。这一个改动，同时决定了它们各自能挡住哪些读异常。

五、redo log：和 MVCC 无关，但必须一起讲清

很多人会把 undo log 和 redo log 搞混。它们名字像，作用完全相反：

undo log · 回滚日志
  • 记录修改前的旧值（逻辑日志）
  • 作用：事务回滚 + MVCC 版本链
  • 保证：原子性（A）与隔离性（I）
  • 什么时候能删：没有任何事务再需要它时，由 purge 线程清理
redo log · 重做日志
  • 记录「在某个数据页做了什么改动」（物理日志）
  • 作用：崩溃恢复，把已提交但没落盘的数据补回来
  • 保证：持久性（D）
  • 循环写：写满就覆盖，靠 checkpoint 推进
类比：装修队的两本本子

undo log 是「原样记录本」：砸墙前先写下「墙在这里、厚 24cm」，业主反悔时能照着砌回去。
redo log 是「施工流水本」：随手记下「3 号房刷了 2 遍漆」。工地突然停电，工人回来照着流水本把没干完的活补上，不用从头再来。

为什么需要 redo log？因为 InnoDB 以 16KB 的数据页为单位管理磁盘，改一行只动了页里几个字节，但要把整页写回磁盘太慢。所以采用 WAL（Write-Ahead Logging，预写日志）：先把改动顺序写进小小的 redo log 并刷盘（顺序写，快），数据页稍后再慢慢刷（随机写，慢）。只要 redo log 落盘了，即使数据页丢了也能恢复。

SQL · redo log 相关参数 
-- 控制 redo log 刷盘时机（8.0）
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';

-- 0：每秒刷一次，事务提交时不刷     → 最快，宕机可能丢 1 秒数据
-- 1：每次提交都刷盘（默认值）        → 最安全，不丢已提交事务
-- 2：提交时只写到 OS 缓存，每秒刷盘  → 折中，MySQL 挂不丢、系统挂可能丢

-- binlog 刷盘参数（注意：binlog 属于 Server 层，不是 InnoDB 的 redo log）
SHOW VARIABLES LIKE 'sync_binlog';
别搞混：redo log vs binlog

redo log 是 InnoDB 存储引擎层独有的、物理的、循环写的崩溃恢复日志；binlog 是 MySQL Server 层的、逻辑的、追加写的归档日志，用于主从复制和数据恢复。两者通过「两阶段提交」保持一致，但职责完全不同。

六、快照读 vs 当前读：MVCC 的适用边界

MVCC 不是万能的，它只管「快照读」。InnoDB 里的读分两类，这是理解模块三、四的关键前提。

两种读的根本区别
维度快照读 Snapshot Read当前读 Current Read
读什么读历史版本（沿版本链找可见的那一版）读最新已提交版本，且必须读最新值
加不加锁完全不加锁必须加锁（记录锁 / 间隙锁）
典型语句SELECT ...（普通查询，不带 FOR UPDATE / LOCK IN SHARE MODE）UPDATE、DELETE、INSERT、SELECT ... FOR UPDATE、SELECT ... LOCK IN SHARE MODE（8.0 也写作 FOR SHARE）
靠什么实现MVCC（隐藏列 + 版本链 + ReadView）锁机制（模块三）
为什么这样设计读操作占绝大多数，不加锁才能高并发写操作必须基于最新值，否则会「改错版本」（丢失更新）
类比：看照片 vs 现场改

快照读就像看老照片——你翻相册里的某一页，不需要打扰正在装修的工人，也不影响他干活。
当前读就像你要亲自动手改这面墙——你必须看到它此刻的真实状态（不能照着三年前的照片砸墙），而且改的时候得把现场围起来（加锁），不然别人同时来改会撞车。

SQL · 一眼分辨两种读 
-- ✅ 快照读：不加锁，走 MVCC 版本链
SELECT * FROM employee WHERE id = 1;

-- ✅ 当前读：加共享锁 S Lock，其他事务能读但不能改
SELECT * FROM employee WHERE id = 1 LOCK IN SHARE MODE;
SELECT * FROM employee WHERE id = 1 FOR SHARE;      -- MySQL 8.0 新写法

-- ✅ 当前读：加排他锁 X Lock，其他事务既不能改也不能加锁读
SELECT * FROM employee WHERE id = 1 FOR UPDATE;

-- ✅ 当前读：DML 天然就是当前读，必须基于最新值修改
UPDATE employee SET salary = salary + 1000 WHERE id = 1;
DELETE FROM employee WHERE id = 1;
INSERT INTO employee VALUES (2, '李四', 6000);
易错点：UPDATE 里的 WHERE 也是当前读

执行 UPDATE employee SET salary=9000 WHERE id=1 时，定位这行的 WHERE 走的是当前读（读最新值 + 加锁），而不是 MVCC 快照。这就是为什么「事务 A 快照读看到的旧值」和「事务 A 执行 UPDATE 实际改的那行」可能不一致——经典面试题「UPDATE 之后 SELECT 结果变了」的根源就在这里。

模块二小结

  1. MVCC 的核心思想：不销毁旧数据，而是保留多版本，让读者自己挑一个合适的版本，从而实现「读写不互相阻塞」。
  2. 三个隐藏列是地基：DB_TRX_ID（谁改的）、DB_ROLL_PTR（上一版在哪）、DB_ROW_ID（无主键时的隐式主键）；DELETE 只打删除标记，物理清理交给 purge。
  3. 版本链由 undo log + DB_ROLL_PTR 串成，最新版本在链头，读取时沿链回溯。
  4. ReadView 四字段：m_ids（活跃事务列表）、min_trx_id、max_trx_id（下一个待分配 ID）、creator_trx_id。
  5. 可见性四步判定：等于自己 → 可见；小于 min → 可见；≥ max → 不可见；落在中间则看是否在 m_ids 里（在=未提交=不可见）。
  6. RR 与 RC 的唯一区别：ReadView 是「首次快照读生成一次、全程复用」还是「每次快照读重新生成」。
  7. undo log 管回滚与 MVCC，redo log 管崩溃恢复（WAL），两者不可混淆；redo log 属于引擎层，binlog 属于 Server 层。
  8. MVCC 只服务快照读；普通 SELECT 是快照读不加锁，UPDATE/DELETE/INSERT/...FOR UPDATE 都是当前读，必须加锁。
模块三 · 核心机制

事务锁体系：从全局锁到临键锁

MVCC 解决了「读」的并发，但「写」必须有排他性。InnoDB 提供了一整套粒度不同的锁，理解它们的加锁范围是搞懂幻读与死锁的前提。

一、先建立全局地图：锁的分类维度

锁看起来种类很多，其实是从三个不同维度切出来的。先看清这张地图，后面就不会乱。

分类维度成员关心什么
按粒度
（锁多大范围）		 全局锁 → 表级锁 → 行级锁 影响多少数据、并发度高不高
按模式
（能不能共存）		 共享锁 S（读锁）、排他锁 X（写锁）、意向锁 IS/IX 多个事务能否同时持有
按范围
（行级锁细分）		 记录锁 Record、间隙锁 Gap、临键锁 Next-Key、插入意向锁 锁住的是「行」还是「行之间的空隙」
最重要的前提

InnoDB 的行锁是加在「索引」上的，不是加在「行」上的。这句话决定了后面所有的加锁范围：走什么索引、索引上匹配到哪些区间，就锁哪些区间。如果 SQL 没走任何索引，InnoDB 只能退化成锁全表所有记录（效果等同表锁）。

二、S 锁与 X 锁：能不能共存的根源

共享锁（Shared，S）和排他锁（Exclusive，X）的兼容关系，是所有加锁行为的基础。记住这张表，其余锁的冲突都是它的延伸。

锁兼容矩阵：✓ 可共存 ／ ✗ 冲突需等待
已持有 ↓ ／ 请求 →S 共享锁X 排他锁
S 共享锁✓ 兼容✗ 冲突
X 排他锁✗ 冲突✗ 冲突
类比：图书馆的书

S 锁 = 借阅证：一本书可以同时发多张借阅证，大家都能看（多人可同时持有 S 锁）。
X 锁 = 独占借出：有人把书借走了要在上面做笔记，这时候其他人既不能借走、也不能拿借阅证看（X 与 S、X 与 X 都冲突）。
但注意：如果只是普通地「翻一下」（快照读），连借阅证都不用办——图书馆有复印本（MVCC 历史版本）。这就是为什么普通 SELECT 不加任何锁。

SQL · 显式加 S 锁 / X 锁 
-- 加 S 锁：我要读，且不允许别人在我读期间修改它
BEGIN;
SELECT * FROM employee WHERE id = 1 LOCK IN SHARE MODE;
-- 此时别的事务：SELECT 可以（快照读不加锁）；LOCK IN SHARE MODE 也可以（S+S 兼容）
--            但 UPDATE / DELETE / FOR UPDATE 会阻塞（S 与 X 冲突）
COMMIT;

-- 加 X 锁：我要改，独占它
BEGIN;
SELECT * FROM employee WHERE id = 1 FOR UPDATE;
-- 此时别的事务：SELECT 仍然可以（走 MVCC）
--            但任何加锁读和写操作全部阻塞
COMMIT;

-- MySQL 8.0 新增：NOWAIT（立即报错不等待）/ SKIP LOCKED（跳过被锁行）
SELECT * FROM employee WHERE id = 1 FOR UPDATE NOWAIT;
SELECT * FROM employee WHERE salary > 3000 FOR UPDATE SKIP LOCKED;
高频踩坑：S 锁导致的死锁

两个事务同时对同一行加 LOCK IN SHARE MODE（S+S 兼容，都成功），然后各自想 UPDATE 这行（都需要 X 锁）。A 等 B 释放 S，B 等 A 释放 S，互相等待 → 死锁。InnoDB 会自动检测并回滚代价较小的那个事务，报错 Deadlock found when trying to get lock。所以「先查再改」的场景应直接用 FOR UPDATE，不要用 LOCK IN SHARE MODE。

三、表级锁：粒度最大的几种

开销最小、加锁最快、并发度最低。分 S 表和 X 表两种。

LOCK TABLES employee READ;    -- 表级读锁，自己只能读不能写，别人只能读
LOCK TABLES employee WRITE;   -- 表级写锁，自己可读写，别人全部阻塞
UNLOCK TABLES;                 -- 释放（事务提交时也会自动释放）

实际很少手动用。但有一种情况会「被动」触发：SQL 无法命中任何索引时，InnoDB 的行锁会退化成锁住扫描到的全部记录，效果接近表锁——这是慢 SQL 拖垮并发的常见原因。

MySQL 5.5 引入，不需要显式声明，访问表时自动加上。增删改查加 MDL 读锁，ALTER TABLE 加 MDL 写锁，读写互斥。

经典生产事故

事务 A 开了个查询但忘记提交（持有 MDL 读锁）→ DBA 执行 ALTER TABLE 加字段（要 MDL 写锁，被阻塞）→ 之后所有对这张表的普通查询也全被阻塞（MDL 写锁申请排在队列里，后续读锁都要等它）→ 整张表瞬间不可用，连接池打满。
预防：DDL 前先查 information_schema.innodb_trx 确认没有长事务；给 DDL 加 lock_wait_timeout；变更走 gh-ost / pt-online-schema-change。

意向锁是表级锁，但它不是用来锁数据的，而是一个声明标记：事务在给某行加 S / X 锁之前，必须先给这张表挂上对应的意向锁。

  • IS（意向共享锁）：我准备给表里某些行加 S 锁
  • IX（意向排他锁）：我准备给表里某些行加 X 锁
类比：餐厅门口的牌子

一家餐厅有 100 个包间。如果有人在 3 号包间用餐，门口的牌子上就挂一个「今日有客」的标记。
现在老板想把整栋楼包下来（加表锁）。他不需要挨个推开 100 个包间去看有没有人（那样代价太大），只要看一眼门口的牌子就知道能不能包。意向锁就是这块牌子——它让「表锁 vs 行锁」的冲突判断从 O(行数) 降到 O(1)。

意向锁兼容矩阵（注意：IS 与 IX 彼此完全兼容）
已持有 ↓ ／ 请求 →ISIXS（表锁）X（表锁）
IS✓✓✓✗
IX✓✓✗✗
S✓✗✓✗
X✗✗✗✗
为什么 IS 和 IX 之间不冲突

因为意向锁只是「声明我要去锁某些行」，两个事务声明的可能是完全不同的行，所以表级别上没有理由互斥。真正的冲突会在行级别去判断。意向锁的存在，纯粹是为了让「申请整张表的 S/X 锁」这个动作能快速失败，而不必逐行检查。

一种特殊的表级锁，用于 AUTO_INCREMENT 列。插入时获取，语句执行完即释放（不是事务结束）。由 innodb_autoinc_lock_mode 控制行为：

值模式行为
0传统模式语句级锁，最保守，自增值严格连续
1连续模式简单插入用轻量互斥量，批量插入用表锁（MySQL 5.7 默认）
2交错模式全部用轻量互斥量，并发最好，但批量插入时自增值可能不连续（MySQL 8.0 默认，因为 binlog 已支持 row 格式）

四、行级锁的三种范围：记录锁、间隙锁、临键锁

这是本篇最需要「看图理解」的部分。三种锁的区别只在于锁住的范围。

记录锁 Record Lock
锁住：单条索引记录

只锁「这一行本身」。别人不能改这行，但可以在它前后插入新行。

间隙锁 Gap Lock
锁住：(a, b) 开区间

只锁「两行之间的空隙」，不锁记录本身。作用是阻止别人往这个空隙里 INSERT —— 专为防幻读而生。

临键锁 Next-Key Lock
锁住：(a, b] 左开右闭

= 记录锁 + 间隙锁。InnoDB 在 RR 级别下加行锁的默认单位，既锁住记录又锁住它前面的空隙。

区间记法（务必分清开闭）

假设索引上有值 10、20、30，那么整条索引被划分成这些区间：
(-∞,10]、(10,20]、(20,30]、(30,+∞)（最后一个叫 supremum 伪记录，代表「无穷大」）。
临键锁锁的是「左开右闭」区间，比如锁 (10,20] 意味着：20 这条记录被锁，且 11~19 之间的空隙不允许插入。

加锁范围的判定规则（RR 级别下）

    

      

        
场景加什么锁说明

        
          
唯一索引 · 等值查询 · 记录存在退化为记录锁唯一值已确定不可能有第二条，锁间隙没意义，InnoDB 会主动优化掉

          
唯一索引 · 等值查询 · 记录不存在退化为间隙锁（左右相邻记录之间）没有记录可锁，但要防止别人把这个值插进来

          
普通（非唯一）索引 · 等值查询临键锁 + 向后遍历到第一个不满足值时的间隙锁非唯一索引可能有重复值，必须连空隙一起锁

          
范围查询（> / < / BETWEEN）临键锁覆盖整个范围锁住区间内所有记录及其间隙

          
无索引可用锁住全表所有记录及间隙等价于表锁效果，务必避免

          
INSERT插入意向锁 + 记录锁插入意向锁是一种特殊的间隙锁，多个事务往同一间隙的不同位置插入时互不阻塞

          
RC 隔离级别下只有记录锁，间隙锁基本关闭所以 RC 无法防幻读（外键与唯一性检查除外）

        
      

    

  


  

    
五、死锁：并发写不可避免的代价

    
两个事务各自持有对方需要的锁，互相等待，谁也走不动 —— 这就是死锁。


    

      
类比：狭窄走廊里的两个人

      
A 从东边进走廊走到中间，B 从西边进也走到中间，两人面对面，谁也不肯退。这就是死锁。

      InnoDB 的做法是：有个「保安」（死锁检测机制）不断巡视，一旦发现有人僵住了，就把「行李少的那个人」请出去（回滚代价较小的事务），让另一个人先走完。被请出去的人会收到 ERROR 1213: Deadlock found。

    


    

      

        
最常见的死锁模式

        


-- 事务A          -- 事务B
BEGIN;            BEGIN;
UPDATE id=1;  ✔  UPDATE id=2;  ✔
UPDATE id=2;  ⏳ UPDATE id=1;  ⏳
-- 互相等待 → 死锁，一方被回滚

        

      

      

        
四种预防手段

        
    
          
  1. 固定加锁顺序：所有业务都按 id 从小到大更新，破坏「循环等待」条件
    2. 
          
  2. 缩小事务范围：事务越短、锁持有时间越少，撞车概率越低
    3. 
          
  3. 让 SQL 走索引：避免行锁退化成全表锁
    4. 
          
  4. 一次锁定所需资源：用 FOR UPDATE 一次锁够，别分多次
    5. 
        

      

    


    

      SQL · 排查死锁与锁等待

-- 查看最近一次死锁的详细信息（最常用）
SHOW ENGINE INNODB STATUS\G   -- 看 LATEST DETECTED DEADLOCK 段

-- MySQL 8.0：查当前谁在等锁、被谁挡住
SELECT * FROM performance_schema.data_locks;          -- 当前持有的锁
SELECT * FROM performance_schema.data_lock_waits;     -- 锁等待关系
SELECT * FROM sys.innodb_lock_waits;                  -- 可读性最好的视图

-- MySQL 5.7 用这几个（8.0 已移除）
-- information_schema.INNODB_LOCKS / INNODB_LOCK_WAITS / INNODB_TRX

-- 锁等待超时时间（默认 50 秒，超时不是死锁，报 1205 Lock wait timeout）
SHOW VARIABLES LIKE 'innodb_lock_wait_timeout';

-- 死锁检测开关（高并发热点行场景可关闭，改为依赖超时，需评估）
SHOW VARIABLES LIKE 'innodb_deadlock_detect';

    


    

      
区分两种报错

      
ERROR 1213 Deadlock found = 死锁，InnoDB 主动检测并立刻回滚一方；

      ERROR 1205 Lock wait timeout exceeded = 锁等待超时（默认等 50 秒还没等到），不是死锁，只是排队太久。两者的排查思路完全不同。

    

  


  
  

    
模块三小结

    
    
      
  1. 三个分类维度：按粒度（全局锁 / 表锁 / 行锁）、按模式（S / X / 意向锁）、按范围（记录锁 / 间隙锁 / 临键锁）。
    2. 
      
  2. InnoDB 行锁加在索引上，不是加在行上。没有索引可用时会退化成锁全表记录。
    3. 
      
  3. S 与 S 兼容，S 与 X、X 与 X 都冲突；但普通 SELECT 是快照读，连 S 锁都不加。
    4. 
      
  4. 意向锁（IS/IX）是表级声明标记，让表锁与行锁的冲突判断从逐行检查降为 O(1)；IS 与 IX 彼此完全兼容。
    5. 
      
  5. MDL 元数据锁自动加，长事务 + DDL 是典型生产事故来源。
    6. 
      
  6. 三种行锁范围：记录锁锁单行、间隙锁锁开区间 (a,b) 只挡 INSERT、临键锁 (a,b] = 记录锁 + 间隙锁，是 RR 下的默认加锁单位。
    7. 
      
  7. 加锁范围会退化：唯一索引等值命中 → 记录锁；唯一索引等值未命中 → 间隙锁；RC 级别 → 基本只有记录锁。
    8. 
      
  8. 死锁由 InnoDB 自动检测并回滚代价小的一方；预防靠固定加锁顺序、缩短事务、走索引。

一句话总结关系

      
MVCC 负责「让读不用等」，锁负责「让写不打架」。它们不是二选一的替代关系，而是互补共存：同一条 UPDATE 语句里，两者甚至会同时出现——用锁保证独占，用 undo log 生成新版本供别的快照读使用。

    

  


  

    
二、为什么快照读不需要加锁？

    
这是理解 MVCC 价值的关键一问。答案藏在「读操作到底需要什么保证」里。


    
推理链条

    

      

        
① 读操作的需求是「看到一个自洽的数据状态」

        
它不要求「看到此刻绝对最新的值」，只要求「我看到的这一份内部不矛盾、且是某个真实存在过的状态」。

      

      
↓

      

        
② undo log 里恰好保存了所有历史状态

        
每次修改都留下旧版本，这些旧版本都是「真实存在过的自洽状态」。

      

      
↓

      

        
③ ReadView 能精确定位「我该看哪个版本」

        
通过比较事务 ID，判断哪些版本在我开始前已提交。

      

      
↓

      

        
④ 既然能直接读到满足要求的历史版本，就没必要阻塞写事务

        
读操作对旧版本的访问，与写操作对新版本的修改，作用在不同的数据版本上，天然无冲突 → 不需要锁。

      

    


    

      
类比：Google Docs 的历史版本

      
同事正在文档里大改第 3 章（写事务持有 X 锁）。你想看这份文档，不需要等他改完——你打开「历史版本」，选昨天的快照来看（快照读）。你们操作的是不同的版本副本，谁也不影响谁。

      但如果你要亲自上手改第 3 章，那就必须先等他改完并保存（当前读 + 加锁），否则你俩的修改会互相覆盖。


      本质：读旧版本 = 无冲突；写最新版本 = 有冲突。这就是 MVCC 能实现「读不阻塞写、写不阻塞读」的全部原因。

    


    
反过来：为什么当前读必须加锁？

    
设想 UPDATE account SET balance = balance - 100 WHERE id = 1 不加锁会发生什么：

    

      

        不加锁的后果 —— 丢失更新（Lost Update）
        
时刻事务 A事务 Bbalance

        
          
T1读到 balance = 10001000

          
T2读到 balance = 10001000

          
T3计算 1000−100=900，写回900

          
T4计算 1000−200=800，写回800 ✗

          
结果正确值应是 700，A 扣的 100 元凭空消失了 —— B 基于过期数据覆盖写入

        
      

    

    
根源在于：写操作必须基于「最新值」计算，而 MVCC 提供的是「历史值」。所以当前读必须绕过版本链读最新数据，并用 X 锁保证「从我读到、到我写回」这段时间里没人能插进来改。这就是 FOR UPDATE 的意义。

  


  

    
三、核心问题：RR 级别下幻读是怎么被解决的？

    
SQL 标准说「RR 不解决幻读，要靠 SERIALIZABLE」。但 InnoDB 在 RR 下用「MVCC + 间隙锁」的组合，把幻读基本解决了。关键在于要分清「哪种读发生的幻读」——因为两种读的解决手段完全不同。


    
    

      

        
交互演示：两种幻读场景与对应的解决机制

        
点击场景，再逐步播放时间线

      


      

        
        
        
      


      

        

          

            场景说明
            

          

        


        

          

            
事务 Atrx_id=200

            

          

          

            
事务 Btrx_id=201

            

          

        


        

          
          
          
          
          0 / 0
        

        

      

    


    
路径一：快照读的幻读 —— MVCC 直接免疫

    
RR 下，事务 A 只在第一次快照读时生成 ReadView，之后全程复用。事务 B 后续插入的新行，其 DB_TRX_ID 必然 ≥ A 的 max_trx_id，根据可见性判定第三步，直接判为不可见。

    

      
机制解释

      
所以在 RR 下，A 无论查多少次，看到的永远是首次快照那一刻的世界，B 插入的新行对 A 永远隐身。快照读的幻读被 MVCC 天然挡住，压根不需要加锁。

    


    
路径二：当前读的幻读 —— 间隙锁出手

    
但如果 A 用的是 SELECT ... FOR UPDATE 或直接 UPDATE ... WHERE 范围条件，那就是当前读，MVCC 不介入，必须靠锁。此时 InnoDB 会加临键锁，不仅锁住范围内已存在的记录，还锁住记录之间以及范围边界的间隙。B 想 INSERT 到这个间隙里，会立刻被阻塞，直到 A 提交。

    

      SQL · 间隙锁挡住幻读插入

-- 表 employee，id 为主键，现有 id = 5, 10, 15

-- 事务 A
BEGIN;
SELECT * FROM employee WHERE id > 7 AND id < 14 FOR UPDATE;
-- 加锁范围：临键锁 (5,10] + (10,15]
-- 意味着 id 在 6~14 之间的任何新记录都无法插入

-- 事务 B（此时执行）
BEGIN;
INSERT INTO employee VALUES (12, '王五', 7000);
-- ⏳ 阻塞！插入意向锁与 A 的间隙锁冲突
-- 一直等到 A 提交或回滚；若超过 innodb_lock_wait_timeout 则报 1205

-- 事务 A
COMMIT;   -- 释放锁，B 的 INSERT 才得以完成

    


    

      
RR 下幻读仍可能发生的破口（高频面试点）

      
InnoDB 的 RR 并没有 100% 消灭幻读。当一个事务里快照读和当前读混用时，破口就出现了：

      
    
        
  1. 事务 A 先做快照读 SELECT * FROM employee WHERE id=12 → 没有这行，生成 ReadView
    2. 
        
  2. 事务 B INSERT id=12 并 COMMIT（A 没有加锁，所以 B 不会被阻塞）
    3. 
        
  3. 事务 A 再快照读 → 仍然看不到（MVCC 挡住了）
    4. 
        
  4. 事务 A 执行 UPDATE employee SET salary=1 WHERE id=12 → 当前读！读到了 B 插入的行并成功修改
    5. 
        
  5. 事务 A 再快照读 → 这行现在出现了（因为 trx_id 变成了 A 自己，判定第一步即可见）→ 幻读发生
    6. 
      

      
结论：MVCC 只能保证「快照读之间」不出现幻读；一旦掺入当前读，就可能看到「新出现的行」。真正要彻底防幻读，必须在事务一开始就用 SELECT ... FOR UPDATE 加锁读，把间隙锁住。

    

  


  

    
四、MVCC 与锁在同一条语句里的协作

    
最容易被忽略的一点：一条 UPDATE 语句，MVCC 和锁是同时参与的。


    

      

        Step 1
        
当前读定位目标行 + 加 X 锁

        
按索引找到要改的行，读最新版本，加排他锁；RR 下还会加上间隙锁防止范围内插入。

      

      
↓

      

        Step 2
        
把旧值写入 undo log，生成新版本

        
MVCC 在这里介入：旧值不销毁，而是存进 undo log；行记录的 DB_TRX_ID 更新为当前事务 ID，DB_ROLL_PTR 指向刚写入的 undo 记录。

      

      
↓

      

        Step 3
        
写 redo log（prepare）→ 更新内存数据页

        
WAL 机制保证崩溃可恢复。

      

      
↓

      

        Step 4
        
COMMIT：redo log 标记 commit，但锁不一定立刻全放

        
提交后 X 锁释放；但 undo log 不能马上删——只要还有老事务的 ReadView 可能需要这个版本，就得留着，等 purge 线程后续清理。

      

    


    

      
关键洞察

      
锁保护的是「写的那一刻」，MVCC 服务的是「写之后的所有读者」。写事务加锁期间，别的快照读照样能跑（读旧版本）；写事务提交后，锁没了，但它留下的 undo 版本还在为老事务的 ReadView 服务。两套机制在时间上是接力关系，不是竞争关系。

    

  


  

    
五、RC vs RR：该选哪个

    
既然 RR 更强，为什么很多互联网大厂反而把线上库改成 RC？因为间隙锁是把双刃剑。


    

      

        
对比项RC 读已提交RR 可重复读（默认）

        
          
ReadView 生成每次快照读重新生成首次快照读生成，全程复用

          
间隙锁基本不加（除唯一性检查、外键）大量使用临键锁

          
幻读会发生快照读免疫；当前读靠间隙锁；混用时仍有破口

          
并发度高（锁范围小）相对低（锁范围大）

          
死锁概率低高（间隙锁容易交叉等待）

          
binlog 格式要求必须用 ROW 格式（STATEMENT 下主从可能不一致）STATEMENT / ROW 均可

          
适用场景高并发 OLTP、互联网业务（阿里等大厂常见选择）需要严格可重复语义、报表统计、默认保守配置

        
      

    


    

      
类比：小区门禁的两种策略

      
RR 像「整层楼连走廊一起封锁」：你在一户施工，整层楼道都不许别人进（临键锁锁了记录也锁了间隙）。绝对安全，但邻居都被挡在外面，还容易两人在楼道口对撞（死锁）。

      RC 像「只锁你家的门」：别人照常走楼道，可以去看看隔壁（只加记录锁）。通行效率高，但偶尔会有人突然出现在你意想不到的地方（幻读）。

      选哪个取决于你更怕「撞车」还是更怕「看到意外的人」。

    

  


  
  

    
模块四小结

    
    
      
  1. 分工：MVCC 让「读不用等」，锁让「写不打架」；两者互补共存，不是替代关系。
    2. 
      
  2. 快照读不加锁的根本原因：读者访问的是旧版本，写者修改的是新版本，作用在不同数据上，天然无冲突。
    3. 
      
  3. 当前读必须加锁的根本原因：写必须基于最新值计算，若基于 MVCC 的历史值会造成丢失更新。
    4. 
      
  4. RR 解决幻读的两条路径：快照读的幻读由 MVCC（ReadView 复用）免疫；当前读的幻读由临键锁 / 间隙锁阻止 INSERT。
    5. 
      
  5. 破口：快照读与当前读混用时仍可能幻读——UPDATE 改了 B 新插入的行后，A 的快照读就能看见它了。要彻底防幻读须一开始就 FOR UPDATE。
    6. 
      
  6. 一条 UPDATE 里两者协作：先当前读加 X 锁定位 → 旧值写 undo log 生成新版本（MVCC 介入）→ redo log 保持久 → 提交后锁释放但 undo 版本继续服务老事务。
    7. 
      
  7. RC 与 RR 的取舍：RC 并发高、死锁少，但需 ROW binlog 且不防幻读；RR 语义强但间隙锁易致死锁。
    8.

五个场景横向对比：一眼看懂谁在起作用

    

      

        
          
场景读类型是否阻塞起作用的机制关键结论

        
        
          

            ① 并发快照读同一行
            快照读
            完全不阻塞
            MVCC（各自的 ReadView）
            读操作之间永不冲突，连锁都不生成
          

          

            ② A 改 / B 读（RR vs RC）
            快照读
            不阻塞
            MVCC + undo log 版本链
            RR 看旧值（可重复读），RC 提交后看新值
          

          

            ③ 两个事务改同一行
            当前读
            B 阻塞等待
            X 记录锁
            写写必须串行，否则丢失更新
          

          

            ④ 范围查询 + 插入（幻读）
            当前读
            B 的 INSERT 阻塞
            临键锁 / 间隙锁
            锁住「空隙」才能挡住幻影行
          

          

            ⑤ 交叉更新两行（死锁）
            当前读
            互相等待 → 一方被回滚
            X 锁 + 死锁检测
            固定加锁顺序是最有效的预防手段
          

        
      

    


    

      
贯穿五个场景的一条主线

      
看这五行对比会发现一个清晰规律：只要涉及的操作里有「快照读」，就一定不阻塞，靠的是 MVCC；只要两边都是「当前读」，就可能阻塞甚至死锁，靠的是锁来仲裁。所以判断一个并发场景会不会卡住，第一步永远是：先分清这两条 SQL 各是快照读还是当前读。

      验证场景 ②：RR 下的可重复读

/* ---- 窗口 A ---- */              /* ---- 窗口 B ---- */
BEGIN;
SELECT salary FROM employee
  WHERE id=1;   -- 5000
                                     BEGIN;
                                     UPDATE employee
                                       SET salary=9000 WHERE id=1;
                                     COMMIT;
SELECT salary FROM employee
  WHERE id=1;   -- 仍是 5000 ✔
COMMIT;
SELECT salary FROM employee
  WHERE id=1;   -- 变成 9000（新事务、新 ReadView）

    


    

      验证场景 ④：间隙锁挡住 INSERT

/* ---- 窗口 A ---- */              /* ---- 窗口 B ---- */
BEGIN;
SELECT * FROM employee
  WHERE id > 5 AND id < 15
  FOR UPDATE;
-- 加临键锁 (5,10] (10,15]
                                     BEGIN;
                                     INSERT INTO employee
                                       VALUES(12,'新人',7000);
                                     -- ⏳ 卡住，一直等待…

/* 第三个窗口查锁等待 */
SELECT * FROM sys.innodb_lock_waits\G   -- 8.0

COMMIT;                              -- B 的 INSERT 立刻返回成功

    


    

      验证场景 ⑤：制造一次死锁

/* ---- 窗口 A ---- */              /* ---- 窗口 B ---- */
BEGIN;                               BEGIN;
UPDATE employee SET salary=salary+1
  WHERE id=1;   -- 拿到 id=1 的 X 锁
                                     UPDATE employee SET salary=salary+1
                                       WHERE id=5;  -- 拿到 id=5 的 X 锁
UPDATE employee SET salary=salary+1
  WHERE id=5;   -- ⏳ 等 B
                                     UPDATE employee SET salary=salary+1
                                       WHERE id=1;  -- ⏳ 等 A → 死锁！

-- 其中一个窗口立刻报错：
-- ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction

-- 查看死锁详情
SHOW ENGINE INNODB STATUS\G   -- 找 LATEST DETECTED DEADLOCK 段

    


    

      
验证提示

      
两个终端必须同时保持事务开启（BEGIN 后不要急着 COMMIT），否则锁一释放就看不到阻塞现象了。命令行客户端可以用 mysql -u root -p -t 让输出以表格形式显示，更易读。

    

  


  
  

    
模块五小结 · 也是全篇总结

    
    
      
  1. 判断并发行为的第一步：分清每条 SQL 是快照读（普通 SELECT）还是当前读（DML / FOR UPDATE / LOCK IN SHARE MODE）。
    2. 
      
  2. 快照读永不阻塞：走 MVCC，各自用 ReadView 沿版本链找可见版本，连锁结构都不生成。
    3. 
      
  3. 当前读之间会阻塞：X 锁互斥，后来者进入等待队列，超过 innodb_lock_wait_timeout（默认 50 秒）报 1205。
    4. 
      
  4. 间隙锁是 RR 防幻读的关键：锁住索引记录之间的空隙，让 INSERT 无法凭空造出「幻影行」。
    5. 
      
  5. 死锁无法完全避免，只能降低概率：固定加锁顺序、缩短事务、让 SQL 走索引；真发生了由 InnoDB 自动检测并回滚代价小的一方。
    6. 
      
  6. MVCC 与锁是接力而非竞争：写事务用锁保证独占，同时通过 undo log 生成新版本；提交后锁释放，旧版本继续服务还没结束的老事务。
    7. 
      
  7. 一句话记住整篇：读看老照片（MVCC），写要独占现场（锁）；RR 把「现场周围的空地」也围起来（间隙锁），所以别人没法凭空塞东西进来（幻读）。
    8.
